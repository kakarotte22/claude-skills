# WikiSkill：把执行经验自动编译成持久知识，并驱动技能演化闭环

源自论文《WikiSkill: Compiling Agent Experience into Persistent Knowledge for
Skill Evolution》(Google Research, arXiv:2608.27454) 的三层知识架构与演化循环，
并针对 Claude Code 环境做了本土化适配：

> raw 经验 → 结构化 wiki patterns → 候选技能（原子提案）→ 验证集门控 →
> 接受则沉淀 / 拒绝则回滚，wiki 永不回滚、持续累积。

## 核心思想

- 经验只有在被**结构化沉淀**后才能跨任务复用，否则每次都在原地重新踩坑。
- 技能改动不能"感觉有用就直接上"：每个提案必须在**验证任务集**上证明自己
  （得分严格超过历史最佳才接受），否则回滚。这防止技能库被无依据的修改污染。
- wiki 是**无条件累积**的知识层：无论提案被接受还是拒绝，pattern、logs、
  审计记录全部保留，为下一轮提案提供越来越完整的依据。

## Workspace 固定路径与初始化

所有经验与演化状态统一沉淀到固定路径，确保知识跨会话累积、不分散：

```
~/.claude/wikiskill-workspace/
```

**每次执行前，先完成初始化（建目录）**：若目录不存在则创建，命令如下：

```bash
mkdir -p ~/.claude/wikiskill-workspace/raw \
         ~/.claude/wikiskill-workspace/wiki/patterns \
         ~/.claude/wikiskill-workspace/skills \
         ~/.claude/wikiskill-workspace/checkpoints
```

并确保以下基础文件存在（不存在则用空模板创建）：
- `wiki/index.md`（空索引）
- `wiki/logs.md`（空日志）
- `wiki/skill-impact.md`（空审计日志，格式见下文）
- `state.md`（演化状态：当前迭代轮次 k、历史最佳得分 ℛ_best、当前已接受的技能清单）

## 三层知识架构 + 演化支撑层

```
~/.claude/wikiskill-workspace/
├── raw/        # 原始经验：完整执行轨迹、对话记录、复盘原文，只追加不改
├── wiki/       # 沉淀后的知识：结构化、累积、只增不减、从不回滚
│   ├── index.md            # 目录索引，列出所有 pattern 及一句话摘要
│   ├── patterns/           # 模式页：每页记录一类失败模式或成功策略
│   ├── logs.md             # 沉淀日志：何时从哪些素材提炼了什么
│   └── skill-impact.md     # 审计日志：每轮提案的元数据、diff、验证得分、接受/拒绝
├── skills/     # 技能本体（门控发生在这里）：接受后的技能留档本体
│   └── <skill-name>/
│       ├── SKILL.md        # 技能完整内容（后续执行时全文引用）
│       └── PURPOSE.md      # 该技能解决什么问题、由哪些 pattern 归纳而来
├── checkpoints/    # 回滚快照：每轮提案应用前的技能目录备份
└── state.md        # 演化状态：k、ℛ_best、当前技能集 S
```

## 核心原则：workspace 是全量汇总，门控发生在本体，分流只是接受后的同步

**`~/.claude/wikiskill-workspace/` 是唯一、永久的经验总库。任何经验都永久保留一份在这里。**

- 技能提案**先应用到 workspace 的 `skills/` 本体上**，验证门控也针对本体进行；
  **只有被接受的技能**才分流同步到 `~/.claude/skills/` 等使用现场。这样回滚
  只需恢复 workspace 内的 checkpoint，不触碰已分发的副本。
- 分层判定与"分流到别处"（写 CLAUDE.md / 归到 skill 的 references / 发布技能）
  **只是为了让经验在后续场景被有效复用所做的复制同步，绝不从 workspace 移除或覆盖**。
- 顺序永远是：**先落到 workspace（留档+门控）→ 验证通过后才分流同步（复用）**。

## 两种运行模式

| 模式 | 触发条件 | 行为 |
|------|------|------|
| **演化模式**（完整闭环） | 用户提供了**可判定的任务集**：训练任务 + 验证任务，且每个验证任务有明确通过判据（预期输出 / 可执行校验命令 / 明确成功标准） | 运行 Inference → Wiki 维护 → 原子提案 → 验证门控 → 接受/回滚 的完整循环 |
| **提取模式**（退化流程） | 用户只提供复盘素材 / 历史轨迹，无可判定任务集 | 只做"raw → patterns → 分流"，技能直接沉淀，跳过门控与回滚（此时须在 logs.md 中注明"提取模式，未经门控验证"） |

两种模式下 wiki 层的维护流程完全相同，区别仅在技能是否经过门控。

## 演化闭环（完整流程）

对照论文的四个组件。每轮迭代 k = 1…K（K 由用户指定或默认持续到无新素材）：

### 0. 准备与基线（仅第一轮）

1. 确认训练任务集 𝒟_train 与验证任务集 𝒟_val，每个验证任务附通过判据。
2. 若 `state.md` 中无 ℛ_best：**用当前技能集（首次为空技能集）跑一遍验证任务**，
   得到基线得分 ℛ_best = ℛ(𝒯_val,0)，写入 `state.md`。
3. 若 ℛ_best 已达满分（1.0），直接终止并报告。

### 1. Inference：训练 rollout

- 用**当前已接受的技能集 S** 执行训练任务：将 S 中每个技能的 SKILL.md **全文注入**
  执行上下文（不做检索/摘要，消除触发失败这个混淆变量）。
- **训练 rollout 期间禁止访问 wiki 层**（论文消融结论：训练期读 wiki 会让经验
  绕过技能层，降低轨迹对技能开发的价值）。wiki 只供 Wiki 维护者和提案者使用。
- 每条轨迹完整落 `raw/`（含推理过程、工具调用、输出、最终结果、成功/失败判定），
  只追加不改写。

### 2. 采样

- 若轨迹量大，从本轮训练轨迹中**按成功/失败分层采样**一个子集 𝒯_sample,k
  供 Wiki 维护者分析（两类都要覆盖，失败轨迹优先多采），控制上下文消耗。
- 被采样排除的轨迹仍保留在 `raw/`，只是本轮不参与提炼。

### 3. Wiki 维护（Wiki Maintainer）

输入：现有 wiki + 𝒯_sample,k。对失败轨迹做根因分析、从成功轨迹提取成功策略：

- 对每条经验做根因分析，抽象出**可复用规律**，写成 markdown pattern 页，每页至少包含：
  - **触发条件**：什么场景/信号下会出现这个问题（或该策略适用）。
  - **现象**：成功/失败的具体表现。
  - **根因**：为什么会这样（失败模式尤其要挖根因）。
  - **可操作对策**：下次遇到该怎么做/怎么避免（必须可执行，拒绝空话）。
  - **来源**：指向 `raw/` 中对应的原始记录。
- 写入规则：优先**增量更新**已有 pattern（同类经验合并，patch 式追加/替换/插入），
  确有新规律才新建页面；更新 `index.md`，追加 `logs.md`。
- 每轮不设新增/更新 pattern 数量上限，由素材决定。

### 4. 技能提案（Wiki-Informed Skill Proposer，原子提案）

- 以 ReAct 方式自主工作，**输入不是全量轨迹**，而是：
  - `wiki/index.md`（wiki 索引）；
  - `wiki/skill-impact.md`（历史提案审计，**避免重复提出已被拒绝的修改**）；
  - 本轮所有训练任务的结果摘要（pass/fail、实际输出、预期输出）。
- 可按需 `Read` 特定 pattern 页和 `raw/` 轨迹做根因诊断，再决定提案。
- **每轮只产生一个原子提案**：针对**单个技能**，要么新建，要么对现有 SKILL.md
  做增量 patch 编辑（不整篇重写）。同时在 `PURPOSE.md` 中维护技能 ↔ patterns
  的溯源关系。

### 5. 应用与快照

- 应用提案前，先备份将被修改的技能目录：

```bash
cp -R ~/.claude/wikiskill-workspace/skills/<name> \
      ~/.claude/wikiskill-workspace/checkpoints/iter<k>-<name>
```

- 然后把提案应用到 workspace 的 `skills/` 本体（新建技能则新建目录）。
- **此时尚不分发到 `~/.claude/skills/`**，门控通过后才分发。

### 6. 验证与门控

- 用候选技能集 S'_k（= 应用提案后的本体）在验证任务集 𝒟_val 上执行：
  技能全文注入、禁读 wiki，与训练 rollout 条件一致。
- 评分 ℛ = 通过任务数 / 验证任务总数。判定尽量自动（运行校验命令 / 对比预期输出），
  无法自动判定的任务向用户确认并如实记录。
- **接受判据：ℛ(𝒯_val,k) > ℛ_best（严格大于）**
  - **接受**：保留修改，更新 `state.md` 中的 ℛ_best 与技能清单，**此时才分流分发**
    （复制到 `~/.claude/skills/<name>/`，并按需做 references 同步，见下文）。
  - **拒绝**：回滚——

```bash
rm -rf ~/.claude/wikiskill-workspace/skills/<name> && \
cp -R ~/.claude/wikiskill-workspace/checkpoints/iter<k>-<name> \
       ~/.claude/wikiskill-workspace/skills/<name>
# 若提案是新建技能且被拒绝：直接 rm -rf 新建目录即可（无需恢复）
```

- **wiki 层（patterns、logs、index）从不因拒绝回滚**；发现 pattern 写错时，
  在原处标注修正并写入 logs.md。

### 7. 审计记录（harness 程序化追加）

验证后立即向 `wiki/skill-impact.md` 追加一条：

```markdown
## 迭代 k — <日期>
- 提案：<创建/修改> 技能 <name>（一句话意图）
- diff：<修改内容的 unified diff 或变更摘要>
- 验证得分：ℛ = <通过数>/<总数> = <x.xx>（当前 ℛ_best = <x.xx>）
- 结果：✅ 接受（ℛ_best 更新为 <x.xx>）/ ❌ 拒绝（技能回滚至 checkpoint，wiki 保留）
```

这份审计日志是后续提案者最重要的输入之一：反复失败的修改方向会在这里现形。

### 终止条件

- ℛ_best 达到满分 1.0 → 提前终止；
- 达到用户指定的迭代次数 K；
- 连续多轮无新素材且提案者基于 skill-impact 判断无值得尝试的方向 → 终止并汇报。

### 闭环一图流

```
        ┌──────────────────────────────────────────────┐
        │  ① Inference：用技能集 S 跑训练任务（禁读 wiki）│
        │     ↓ 轨迹落 raw/                              │
        │  ② 采样：成功/失败分层                          │
        │     ↓                                          │
        │  ③ Wiki 维护：提炼/合并 patterns（永不回滚）     │
        │     ↓                                          │
        │  ④ 提案：查 index + skill-impact + 结果摘要，    │
        │     自主 Read patterns/raw，产出单个原子提案      │
        │     ↓                                          │
        │  ⑤ 应用到 workspace 本体 + checkpoint 快照       │
        │     ↓                                          │
        │  ⑥ 验证：𝒟_val 上评分                           │
        │     ├─ ℛ > ℛ_best → 接受：更新 ℛ_best，分流分发  │
        │     └─ 否则    → 回滚技能本体（wiki 保留）        │
        │     ↓                                          │
        │  ⑦ 追加 skill-impact.md 审计记录                │
        └────────────────────── 循环 ────────────────────┘
```

## 提取模式（退化流程，无可判定任务集时）

当用户只提供复盘素材/历史轨迹时，跳过 ①⑤⑥⑦，只执行：

1. **归置原始经验 → `raw/`**（留档本体，只追加不改写，保留时间戳与来源）。
2. **提炼模式 → `wiki/patterns/`**（同上演化闭环第 3 步）。
3. **分流复用**（同上演化闭环第 6 步"接受后"的分发逻辑，但未经门控）。
4. 在 `logs.md` 注明"提取模式，未经门控验证"，提醒后续使用时注意置信度。

## 经验分层判定（先留档，再决定如何分流复用）

收到经验时，**先写入 workspace 留档**，再按下面三类判定"如何把副本同步到别处以复用"。一条经验只有一个留档本体，但可以有多种复用分流：

| 类型 | 特征 | 判据 | 复用分流去处 |
|------|------|------|------|
| **常驻型硬约束** | 跨项目、高频、每次必须生效的一条规则/约定 | "下次需要'永远记得这条规则'" | 同步写入**全局 CLAUDE.md**（`~/.claude/CLAUDE.md`） |
| **按需型经验/技巧** | 低频、特定场景、按需检索 | "下次遇到 X 时，需要'查到这条坑'" | 复制到**对应 skill 的 `references/`** 并加引用（见下） |
| **可复用技能** | 一组可执行的多步流程/SOP | "下次遇到，需要'照这套步骤做一遍'" | 归纳为 **skill** 并发布到 `~/.claude/skills/`（演化模式下须先过门控） |

判据一句话：需要"永远记得"→CLAUDE.md；需要"查到这条坑"→references；需要"照着步骤做"→独立 skill。无论去哪个去处，workspace 里的留档本体都保留。

## 复用分流：把副本同步到对应 skill 的 references 目录

按需型经验在 workspace 留档后，**另外复制一份**到对应 skill 下，让它在正确场景被自动带入。**目标目录是已安装的 skill 位置**：

```
~/.claude/skills/<对应skill>/references/
```

### 分流步骤

1. **定位对应 skill**：根据经验主题，判断它属于哪个已有 skill（如 `dataworks-pyspark`、`dataworks-upload`、`model-train`、`model-deploy`、`logview-stdout` 等）。先 `ls ~/.claude/skills/` 查看已有 skill，优先归入最相关的一个。
2. **复制 reference**：在该 skill 下建 `references/` 目录（不存在则建），把经验写成 markdown 放入，命名 `references/<主题>.md`。内容含：触发场景、现象、根因、可操作对策，并在文末标注"留档本体见 `~/.claude/wikiskill-workspace/...`"。
3. **加引用语句**：在该 skill 的 `SKILL.md` 里补一句"遇到 X 场景时，先阅读 [<主题>.md](目录为：references/<主题>.md)"，让触发该 skill 时能自动读到这份经验。
4. 若该经验 **没有对应 skill 可归**（独立成一类且够常用），则按"归纳技能"流程给它新建一个带触发词的 skill（同样先在 workspace 留档；演化模式下走完整门控）。

## 归纳技能

- 当若干 patterns 指向同一类"可照做的流程"时，归纳为一个技能目录（先在 workspace 的 `skills/` 留档）。
- `SKILL.md` 写技能完整执行方法（把 patterns 的对策串成可照做的流程），并在 frontmatter 的 `description` 里写清**触发词**。
- `PURPOSE.md` 写清该技能解决什么问题、归纳自哪些 pattern。
- **演化模式下：新建/修改技能一律走第 4-7 步的门控流程，验证通过后才复制到 `~/.claude/skills/<name>/`**；提取模式下直接沉淀并复制，同时更新 `skill-impact.md` 记录归纳来源（标注"未经门控"）。

## 提炼时遵循的原则

1. **先留档、后分流**：每份经验先落 workspace 汇总库；技能先过门控，再复制副本到复用现场；workspace 本体永不删除。
2. **门控先行**：技能改动必须"验证得分严格超过 ℛ_best"才接受，否则回滚到 checkpoint；被拒绝不等于失败，它沉淀为 skill-impact.md 里的审计记录。
3. **原子提案**：每轮只改一个技能、只做一类修改，让每次验证得分的归因清晰。
4. **wiki 永不回滚**：workspace 的 patterns/logs 只增不减；错了就在原处标注修正并写进 logs。
5. **去重合并**：新经验先对照已有 pattern/已有 skill 的 reference，同类就补充，不新开文件，避免膨胀。
6. **对策可执行**：每条经验必须落到"下次具体怎么做"，禁止只描述现象不给出路。
7. **单点提炼**：一次聚焦一类问题，把它说透，不贪多求全。
8. **可追溯**：每个 pattern/skill 都要能指回 `raw/` 里的原始经验，保留证据链。
9. **训练期隔离 wiki**：Inference rollout 时技能全文注入、禁读 wiki，保证轨迹反映技能本身的效力。

## 使用方式

- **演化模式**：提供 ① 一批训练任务 ② 一批验证任务（各附通过判据）③ 期望迭代轮数 K（可选），本 skill 自动运行完整闭环，每轮汇报：轨迹结果、pattern 变更、提案内容与 diff、验证得分、接受/回滚决定。
- **提取模式**：直接把一批执行记录、成功失败案例、或复盘文字交给本 skill，自动完成分层、提炼与归档（未经门控，会在 logs.md 标注）。
- 沉淀完成后会告诉你：分了哪些层、新建/更新了哪些 pattern、归档到哪个 skill 的 reference、归纳/修改了哪些技能、各自对应哪些原始素材、门控结果与当前 ℛ_best。
- 后续新经验持续追加即可，知识库不断累积；有新任务集时可随时重启演化闭环，从 `state.md` 恢复上次进度。
